01

Istibqa Ltd · Co-founder & CTO

A guardrailed, data-aware AI copilot

Built · pre-launch Multi-tenant 12 ADRs

Next.js 16 · React 19 · TypeScript · Supabase/PostgreSQL · Anthropic SDK · Stripe · Paystack · WhatsApp Cloud API

Context

Tadhkir is a WhatsApp retention platform for recurring-visit service businesses — dental practices, optical clinics, physiotherapists, salons — across the UK, Gulf, US and Africa. It tracks when each customer is due back and sends a personalised reminder at the right interval for that industry.

Owners kept asking questions the dashboard couldn't answer: which customers am I about to lose, and what should I do about it? The obvious answer was an assistant over their data. The non-obvious part was doing that safely on a platform holding patient and client records.

The problem

An LLM with database access on a multi-tenant platform is a data breach waiting to happen. Three risks had to close before shipping:

  • Cross-tenant leakage. If the model can name which business's data to fetch, a prompt injection can make it name someone else's.
  • PII exposure to a third party. Our published DPA promises customer names and phone numbers never leave the platform. An assistant that reads customer records breaks that promise.
  • Cost as an attack surface. An assistant running on our API credits is a free general-purpose LLM if anyone thinks to use it as one.

What I built

One engine, two surfaces. A single runCopilot() loop drives both the customer-facing Revenue Copilot and the internal Admin Copilot. Each supplies its own system prompt and tool set; the loop, guardrails and limits are identical. Two implementations would have drifted within a month — and the weaker one becomes the vulnerability.

A bounded agent loop. Call the model → execute any tool_use against server-bound context → feed tool_result back → repeat until a text answer, capped at six rounds. The cap matters: an unbounded tool loop is an unbounded bill.

The load-bearing decision

Injection can't talk its way past a function signature.

Tool handlers receive tenant context resolved server-side from the authenticated session, and never accept a tenant selector as a model-supplied argument. The model cannot ask for another business's data because there is no parameter through which to ask. "Only discuss this business" is advisory. This is architectural.

Aggregates only, never people. Tools return counts, rates and buckets — get_business_overview, get_at_risk_summary, get_reminder_activity. When an owner needs an individual record, the copilot points them to the dashboard. The DPA commitment holds because no code path exists to violate it.

A layered guardrail pipeline. Every request from both surfaces runs through one guardedCopilot wrapper: input caps at 30 messages per conversation and 4,000 chars per message; rate limits of 15/min and 200/day per user plus a global daily circuit breaker; injection and exfiltration screening that pattern-checks the latest turn for instruction-override, system-prompt extraction and cross-tenant probes, returning a canned refusal without calling the model so abuse burns no credits; a strike-based cooldown where five flagged requests in ten minutes triggers a 30-minute lockout, handling the determined abuser rather than just the opportunist; and output scrubbing of anything credential-shaped as defence in depth.

Cost control through model tiering. The expensive Sonnet tool loop sits behind a cheap Haiku classifier that runs first and rejects off-scope requests — marketing copy, coding help, general consulting — before any billable frontier call. Persistent off-label use trips the same strike system. The classifier fails open, so an outage degrades to "slightly more expensive" rather than "copilot down."

What I'd highlight in review

The interesting work wasn't prompt engineering. It was deciding which safety properties could be trusted to a prompt and which had to be enforced by the type system and the call graph. Anything a determined user could talk the model out of — tenant scope, PII access — became structural. Anything advisory — tone, refusal style — stayed in the prompt.

Also shipped: multi-market billing across Stripe and Paystack in six currencies; WhatsApp Cloud API messaging in 10 languages; CSV and physical-document ingestion; a tiered affiliate engine with config-driven commission. The copilot engine is unit-tested against a mocked SDK, with Playwright covering end-to-end flows.

02

Minigigs Ltd · Founder & Principal Engineer

Multi-agent code generation with a self-healing loop

Working beta ~67K LOC 7 agents 6 locales

Next.js 16 · React 19 · TypeScript · Prisma 7 · PostgreSQL · Anthropic + OpenAI SDKs · Pinecone · Inngest

Context

AI app builders generate fast demos that tend to be unarchitected and fragile under real users, and they work in English only. Eugenius takes a different position: plan before building, generate natively in the user's own language, and keep running the app after it ships.

The problem

Three engineering problems sit underneath that product bet. A full app build takes minutes, not seconds — so any architecture where a dropped connection or a server restart loses the work is unusable. Frontier-model pricing applied to every step makes the unit economics impossible; not every task in a build needs the most capable model. And generation is the easy half: tools that stop at "here's your code" leave the user alone with a runtime error they can't debug — precisely the user who couldn't write the code in the first place.

What I built

A 7-agent orchestration pipeline. Architect → generator → reviewer → test → deploy, running in parallel where stages are independent and sequentially where one's output is another's input, sharing context as the build progresses. The architect stage is the differentiator: requirements and architecture are settled before generation, so the output is a designed system rather than an accumulation of files.

The load-bearing decision

Durable execution, not a long-lived request.

Every stage runs as a checkpointed background job on Inngest. A build taking several minutes survives restarts and partial failures, resuming from the last completed stage instead of starting over. This was the difference between a demo and something a user can rely on.

Multi-model routing. A router selects per task across Anthropic and OpenAI models by capability, latency and cost. Architecture and review get the strong models; mechanical transforms don't. Single-model architectures are simpler, but they either overpay everywhere or underperform everywhere.

Retrieval plus a correction-learning loop. A Pinecone-backed vector store indexes generated projects and user corrections. When a user edits generated output, the system treats that edit as a signal: it extracts the pattern and feeds it into later generations. No manual labelling, and the system's weak spots get corrected by the people best placed to notice them.

Self-healing after deploy. Runtime error signals from deployed applications route back into the agent loop, which diagnoses and patches the live app. This closes the build-and-run gap pure code-generation tools leave open — and it's only possible because the platform owns the deployment, not just the codebase.

Language-native generation. Rather than generating English and machine-translating it, the generation path writes natively in the target language. Supporting this meant building a compile-time i18n system across six locales where locales are compiled artefacts advertised from a single config, rather than runtime translation with its latency and quality costs.

What I'd highlight in review

The codebase runs under CI gates on lint, typecheck and coverage, with strict TypeScript, conventional commits and ADRs for significant decisions. Ahead of launch I ran a full self-audit of the platform, and it found real security gaps — including two critical. I documented them honestly in the repo and drove a remediation sprint rather than shipping on a "production-ready" claim the code hadn't yet earned.

That audit is the part of this project I'd most want to talk through. It's straightforward to write the marketing sentence; the useful skill is auditing your own work adversarially and then acting on what you find when nobody would have known otherwise.

03

Zerli · Senior engineer → platform lead

From legacy single-venue app to multi-tenant SaaS

Preparing launch 4 applications Firebase → Postgres

React Native (Expo) · React · TypeScript · Node.js/Express · PostgreSQL/Supabase · Stripe · Paystack · Sentry

Context

I built the ordering platform for Luciana's Grill from zero — customer mobile apps for iOS and Android, an operator app, a web ordering front end, and the backend behind menu management, order routing and kitchen operations. When the venue wound down, the platform was the asset worth keeping. Zerli is that platform re-architected into a multi-tenant SaaS any restaurant can run on.

The starting point

The honest baseline was a working product carrying real debt. A pre-migration audit found:

  • Signing keystores committed to git in both mobile apps
  • A .env file committed in the web app
  • firebase-admin bundled into the customer mobile app — a server-privilege SDK shipped to end-user devices
  • CORS: * on the backend
  • No TypeScript anywhere, React Navigation v5 (EOL), Create React App (deprecated), a single-file Express backend, and no error tracking on web or backend at all

None of this was surprising for a product built fast to serve one venue. All of it was disqualifying for a platform meant to hold other businesses' payment and customer data.

What I did

Specced before touching code. I wrote a full technical specification — current state, known issues ranked by severity, target state, phased migration — and had it approved before development. On a migration this broad, the specification is the thing that stops it becoming an eighteen-month rewrite.

Closed the security findings first. Credentials out of version control and rotated, the admin SDK removed from the client bundle, CORS locked to known origins. Security debt compounds and can't be shipped on top of.

The load-bearing decision

Sequence the migration. Never run it all at once.

Security, then language, then framework, then data, then tenancy. Migrating four applications, a database and a payment layer simultaneously fails. Sequencing it meant the product stayed shippable throughout.

Modernised in phases. Expo SDK 56 with EAS Build and EAS Update replacing manual keystore handling and CodePush; React Navigation v7; Redux Toolkit replacing bare Redux with thunks; Vite replacing Create React App; strict TypeScript across all four applications; Sentry for crash and error tracking on every surface, including the two that previously had none.

Migrated off Firebase to Postgres. Firestore's document model fought the relational shape of orders, menus and venues. Moving to PostgreSQL — with migration scripts written and reversible — gave real constraints, real joins and a schema that could express tenancy.

Re-architected for multi-tenancy. Tenant data isolation, per-venue configuration, onboarding, and an app-factory build script that produces a branded application per restaurant from shared source rather than forking the codebase per customer. Payments span Stripe and Paystack, covering checkout, webhooks, refunds and reconciliation.

What I'd highlight in review

This is the project where I learned that inheriting your own code is its own discipline. I wrote the original, and the audit that catalogued its problems was an audit of my own work from two years earlier. Writing "keystore committed to git — critical" about your own commit is uncomfortable and exactly the right thing to do; the alternative is a platform that leaks other people's customers.

Colophon

Yes — this page was built with AI. That's the point.

Every system documented above was built by pair-programming with frontier models under a written engineering standard: conventional commits, ADRs for significant decisions, CI gates on lint, typecheck and coverage, and a security audit before launch rather than after.

That's the actual claim. Not that AI wrote some code — anyone can get that. It's that the output holds up to the same review a hand-written system gets, because the judgement about what to build, what to trust the model with, and what to enforce structurally stayed with the engineer. This page is the smallest example: one hand-directed HTML file, no framework, no build step, no third-party requests.
